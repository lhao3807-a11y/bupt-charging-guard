## 一、项目背景与意义

### 1.1 问题提出

随着新能源汽车快速普及，高校充电需求持续增长，而校园充电桩资源增长有限，供需矛盾突出。实际运行中存在两类典型现象：

- **燃油车违规占用充电车位**——蓝牌车辆停在充电位上，导致新能源车无法正常补能；
- **新能源车"充满未移车"**——已完成充电却长时间不驶离，车位周转率被进一步压低。

两类问题目前主要依靠人工巡查处理，效率低、发现不及时、处置缺少结构化记录，难以支撑统计、考核与追责。更关键的是，**"充满未移车"这一状态无法靠单一手段识别**：只看图像无法判断车是否在充电，只看充电桩数据无法判断车位被谁占用。这正是现有方案普遍失效的地方。

### 1.2 项目意义

- **管理侧**：把校园充电车位管理从"人管"推向"数管"，以自动化闭环提升车位周转率、降低人工巡查成本。
- **用户侧**：让真正需要补能的车主能找到可用车位，改善校园充电体验。
- **方法侧**：沉淀"视觉识别 + 设备状态"融合判断的技术路径，可迁移到其他需要区分"合法占用"与"违规占用"的场景。
- **推广侧**：方案部署成本低、模块化可裁剪，凡"有桩、有位、有占用矛盾"的园区、写字楼与公共停车场均可复用。

## 二、项目目标

### 2.1 总体目标

建成一套面向高校校园的**充电车位智能监管系统原型**，完整跑通"**识别—判断—提醒**"业务闭环：摄像头采集图像 → 车辆检测与车牌识别 → 融合充电桩状态 → 规则引擎判定违规 → 短信提醒车主并落库 → 后台可视化管理。

## 三、项目范围与边界

**范围**：校园场景的演示系统原型，完整跑通业务闭环，**不做生产环境部署**。

**明确不做（MVP 边界）**：

| 项 | 处理方式 | 原因 |
|---|---|---|
| 充电桩实时状态 | 采用**模拟数据**，预留 OCPP 适配层 | 运营商接口权限受限，无法获取真实状态 |
| 实时视频流预览 | 仅展示**最近一帧截图**（轮询刷新） | 降低前端与带宽复杂度，演示足够 |
| 车型判定方式 | 由**车牌底色**判定（绿牌 = 新能源 / 蓝牌 = 燃油） | 车辆外观分类准确率不可控，车牌类型是可靠代理 |
| 部署形态 | 推理进程与 Web 服务**拆分为独立进程**，Web 仅读库并供前端 | 避免推理阻塞页面响应 |

> 边界一经确定即写进契约；任何调整须**先改契约 → 全员通告 → 升版本号**，再动代码。

## 四、技术方案

### 4.1 总体架构（五层）

| 层 | 职责 | 关键实现 |
|---|---|---|
| 图像采集层 | 摄像头 / 测试视频 → 定时抽帧 | OpenCV 抽帧，输出标准化帧（RGB，固定分辨率） |
| 智能识别层 | 车辆检测 + 车牌识别（号码 + 颜色/类型） | Ultralytics YOLOv8 + HyperLPR（主）/ PaddleOCR（备选） |
| 数据融合层 | 按车牌号关联车辆与充电桩状态 | MySQL 状态库 + 模拟器 |
| 业务处理层 | 违规判断规则引擎 | Python 规则函数，阈值可配置 |
| 应用展示层 | 后台管理 Web + 报警提示 + 短信提醒 | Vue3 + FastAPI + 短信网关 |

### 4.2 核心业务闭环

```
抽帧 → 车辆检测 → 车牌识别（号码 + 类型）
     → 查库关联（车辆 / 充电桩绑定）→ 获取充电状态（模拟）
     → 违规判断（规则引擎）→ 命中则短信提醒 + 落库
     → 后台可视化展示
```

四条判定规则：

1. 燃油车（蓝牌）占用充电位 → **违规占位**
2. 新能源车未充电且久停 → **异常占位**
3. 新能源车充满超时未驶离 → **充满未移车**
4. 正常充电 → **不提醒**

### 4.3 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 后端 | FastAPI（Python 3.11.x） | 异步框架，接口契约可自动出 OpenAPI |
| 前端 | Vue 3 + Vite + TypeScript + Element Plus | 极简后台，组件成熟、交付快 |
| 数据库 | MySQL 8（开发期 SQLite 等价验证） | 数据访问走 SQLAlchemy，换库只改连接串 |
| 目标检测 | Ultralytics YOLOv8（n/s） | 预训练起步，配合校园场景微调 |
| 车牌识别 | HyperLPR（主）/ PaddleOCR（备选） | 识别号码 + 底色判型 |
| 提醒通道 | 阿里云 / 腾讯云短信 SDK | 沙箱 / 真实双模式，答辩可回落沙箱 |
| 可视化 | ECharts | 统计图表配色统一从设计令牌读取 |

### 4.4 数据模型（核心四表）

| 表 | 关键字段 | 用途 |
|---|---|---|
| `vehicle` | plate(PK) / vtype / owner / phone / created_at | 车辆与车主信息 |
| `charging_pile` | pile_id(PK) / status / bound_plate / start_time / end_time | 充电桩状态（模拟） |
| `occupation_record` | id(PK) / plate / vtype / pile_id / rule_hit / occur_time / notify_status / notify_time | 违规记录，支撑查询与统计 |
| `system_config` | key(PK) / value / note | 阈值参数（`full_timeout_min`、`abnormal_park_min`） |

> 阈值一律从 `system_config` 读取，**严禁硬编码**。

### 4.5 功能模块与负责人

| 模块 | 内容 | 负责人 |
|---|---|---|
| M1 图像采集 | 读视频 / 图片，定时抽帧 | 汤瑾睿 |
| M2 车辆检测 | YOLOv8 检测车辆，输出 bbox + 置信度 | 汤瑾睿 |
| M3 车牌识别 | 定位车牌 → 识别号码 → 判定类型 | 汤瑾睿（算法）+ 吕浩（封装） |
| M4 充电状态模拟 | 车牌↔桩状态种子数据、定时更新、预留 OCPP | 汤瑾睿 |
| M5 违规判断规则引擎 | 四规则判定，阈值可配 | 汤瑾睿 + 吕浩 |
| M6 短信提醒 | 查车主手机号 → 发送 → 记录 | 吕浩（接口）+ 汤瑾睿 |
| M7 后台管理平台 | 车辆信息管理 / 违规记录查询 / 充电状态展示 / 报警统计 / 系统参数配置 / 实时识别预览（六页） | 吕浩（前端 + 接口）+ 吴和庆（UI） |

### 4.6 关键实施策略

本项目最大的不确定性来自计算机视觉模型（环境依赖复杂、数据采集慢、准确率不保证）。为此采用两条工程策略：

1. **契约先行**——数据模型、接口签名、返回结构先写死进 `docs/CONTRACT.md`（唯一事实源），三人并行开发不互相猜测，也不口头约定。
2. **桩替身解耦**——最慢最险的环节先用替身顶上：识别用"识别桩 stub"（读标注 JSON）、短信用"沙箱"（写库 + 日志）。**先用替身证明闭环能跑通，再逐段替换为真实模型与真实短信**。真实实现与替身返回**同一数据结构**，替换时上层零改动。

## 八、质量管理

### 8.1 测试与验收

| 层级 | 手段 | 通过标准 |
|---|---|---|
| 单元测试 | 后端 `pytest`（规则引擎四规则 + 边界用例） | 全过；第 1 周目标 57 项 → 第 2 周 ≥ 70 项 |
| 接口测试 | FastAPI `TestClient` 调用各端点 | 全部端点正常返回 / 错误码正确 |
| 集成测试 | 端到端脚本：识别 → 判定 → 提醒 → 后台可见 | 全流程贯通 |
| 设计走查 | `check_tokens.py` 令牌校验 + 跨页一致性检查单 | **exit 0**，无裸色值 |
| 性能测试 | 准确率评测集、响应时间、24h 稳定性压测 | 满足第二章技术指标 |

### 8.2 代码与交付规范

- **交付前三件套**：`pytest` 全过 + `ruff`/`black` 全过 + 设计令牌脚本 exit 0，**全绿才允许合入**。
- **前端约束**：页面不出现裸色值，一律使用设计令牌变量；表格列严格照契约字段，不自造字段与枚举。
- **后端约束**：阈值一律从 `system_config` 读取，禁止硬编码。
- **每次改动必须伴随 commit**，便于追溯与回滚；每次改动必须编写或更新对应测试。

## 九、风险管理

### 9.1 风险登记表

| # | 风险 | 概率 | 影响 | 应对措施 |
|---|---|---|---|---|
| R1 | **CV 环境装不上**（`ultralytics` / `paddleocr` 依赖冲突） | 中 | 高 | 第 1 周首日试装；失败立即降级为 YOLOv8n + 车牌模板匹配 / `hyperlpr`；实在不行第 2 周继续用替身，**不阻塞其他模块** |
| R2 | **校园数据集不足或采集困难** | 中 | 高 | 合成帧扩增 + 校园实拍结合；标注用 LabelImg / CVAT；按四类各 ≥ 30 张组织 |
| R3 | **准确率不达标**（< 95% / 90%） | 中 | 中 | 扩充校园场景测试集、模型微调、目标跟踪去重、抽帧降频 |
| R4 | **实时性不足**（报警响应 > 5s） | 低 | 中 | 抽帧降频 + 模型轻量化（YOLOv8n）+ 异步处理 + 推理与 Web 拆进程 |
| R5 | **真实充电接口无权限** | 高（已发生） | 低 | 已定策略：模拟数据 + 预留 OCPP 适配层，不阻塞闭环 |
| R6 | **短信密钥申请与计费** | 中 | 低 | 开发期沙箱；答辩前接入真实 API，保留开关可随时回落沙箱 |
| R7 | **MySQL 8 真机未验证**（本机未安装，开发期用 SQLite 等价验证） | 高 | 中 | `schema.sql` 以 MySQL 8 语法交付；第 2 周接真库时补验 `InnoDB`、`ENUM` 等特有语法 |
| R8 | **三人分支分叉导致合并事故** | 中 | 中 | 开工先同步主干；合并前校验分支是否为 `main` 后代，非后代则按目录摘取而非整分支合并 |
| R9 | **前端工期被设计走查拖慢** | 中 | 中 | 第 1/2 页优先于图标与插画；图标第一周允许使用组件库内置图标 |
| R10 | **模型许可合规**（Ultralytics YOLOv8 为 AGPL-3.0） | 低 | 低 | 本项目为校园非商业原型；若后续商业化须评估替代方案或获取商业授权 |

### 9.2 关键路径与决策点

- **关键路径**：数据集采集与标注 → YOLOv8 训练/推理 → 车牌识别调优 → 端到端集成 → 性能达标。
- **主要决策点**：
  1. **第 1 周末**——CV 环境是否可用？决定第 2 周走真实模型还是延长替身周期。
  2. **第 2 周末**——准确率初测结果？决定第 4 周调优投入与目标是否需重新协商。
  3. **第 3 周末**——全链路联调是否稳定？决定是否引入真实短信参与答辩演示。
