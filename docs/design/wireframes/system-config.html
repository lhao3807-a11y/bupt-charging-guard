系统参数配置

阈值取自 system_config 表，本页是这两个数字的唯一修改入口（契约 §7：阈值严禁硬编码）。

! 修改阈值将直接影响规则引擎的判定结果，并联动「违规记录查询」与「报警统计」两页的数字。建议在没有正在进行演示时调整，改完先跑一次识别验证判定符合预期。

确认修改系统参数 ✕
!
即将修改 1 项参数：
full_timeout_min 30 分钟 → 45 分钟
影响面：规则 ③「充满未移车」的判定阈值。改大后，桩充满 30～45 分钟期间不再产生新的违规记录；已落库的历史记录不受影响。

参数影响面（写在页面上，不靠记忆）

两个键各自影响哪条规则、哪一页，必须能一眼查到，否则调试时会来回猜。

参数 → 规则 → 页面

full_timeout_min 规则 ③ 充满未移车（rule_hit = 3）· 影响第 2 页记录与第 4 页黄色分项
abnormal_park_min 规则 ② 异常占位（rule_hit = 2）· 影响第 2 页记录与第 4 页橙色分项
规则 ① 燃油车占位与规则 ④ 正常充电不受这两个阈值控制（前者靠车牌类型判定，后者是「不命中」分支），页面上不要给出误导性的「影响全部规则」文案。

空态与异常态

这一页出问题往往比别处更严重（判定会失真），所以异常态要给出明确的修复动作。

参数键缺失 —— 表格为空

system_config 表为空

说明建表后未写入种子数据。后端启动时会自动建表 + 插种子，若此处为空请先确认 backend/sql/schema.sql 的种子是否执行成功——阈值缺失会让规则 ② ③ 无法判定，不是小问题。

取值非法 —— 行内校验

非法值 − 0 ＋ 分钟
应为 大于 0 的整数（分钟）。填 0 会让规则恒不命中，等于关掉了这条违规判定。

标注说明

契约 §7 明令：阈值一律从 system_config 读取，严禁硬编码。本页是这套约束的 UI 出口。

  1. 表格列 = system_config 全字段：参数键 key / 参数值 value / 说明 note，另加「操作」列。字段与列一一对应，未新增字段。
  2. 只放契约里已有的两个键：本期 CONTRACT.md §7 只定义了 full_timeout_min 与 abnormal_park_min。非阈值键（如后续的 OCPP 开关）按同一张表展示、置为只读并用 tooltip 说明用途，但本期不预造键名——造了就会在联调时对不上。
  3. 行内编辑而非弹窗：只有 2 个值，弹窗反而增加层级。用 el-input-number 行内改，单位「分钟」用 append 后缀，避免用户把单位理解成秒。
  4. 「已修改未保存」必须可见：改动项给主色描边 + 光晕（--brand-primary + --brand-primary-bg），并在表底压一条黄色未保存条（--state-warning-*），列出「哪个键、从多少改到多少」。未改动行的「保存/撤销」置灰，避免误以为整页都要保存。
  5. 保存走二次确认，且把 diff 写进正文：这是全站唯一能改变判定结果的入口，属于高风险操作。确认框里写清「改前 → 改后」和影响面，不做「确定要保存吗」这种无信息量文案。
  6. 不提供「恢复默认」按钮：契约未定义默认值的重置接口，硬做一个只在前端改数字的「恢复默认」会造成「看起来恢复了但库里没改」的假象。需要的键把默认值（30）写在说明列里，用户手动改回去即可。
  7. ⚠️ 待确认（汤瑾睿）：确认框里写了「已落库的历史记录不受影响」——即改阈值不回溯重算历史判定。这是设计侧按「判定发生在落库时刻」推出的行为，需汤瑾睿确认规则引擎实现一致；若引擎会回溯重算，这句话必须删掉并另写说明。
  8. ⚠️ 待确认（吕浩）：保存参数需要写接口（PUT/POST /api/config 之类），契约 §6 尚未定义。第 1 周若不做本页交互，可先只读展示；若要可编辑，须走「先改 CONTRACT.md → @全员 → 升版本号」流程，不得由前端私定路径。
  9. 等宽处理：参数键、阈值数字均用 --font-family-mono + tabular-nums，与全站定长标识一致。
