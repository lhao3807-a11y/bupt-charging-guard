**目标**：第三周末完成 M4/M5/M6 的原型验收，能从网络实拍识别或确定性样例开始，自动判定违规、发送沙箱提醒、更新记录与统计；失败可恢复，同次占用不反复提醒。为第四周性能、稳定性与结题留出完整时间。

**实现方向**：沿用 FastAPI、SQLAlchemy、MySQL 8/SQLite、Vue 3、YOLOv8 与 HyperLPR3。后端统一编排识别、判定和提醒，前端显示结果并提供人工重试；模拟状态与实拍识别的证据分别记录。沙箱发送器返回确定性成功/失败，不依赖运营商账号。

## 2. 本周范围与 D1 必须签定的口径

### 必做范围

自动沙箱提醒；正常不提醒；同次占用判重；失败记录及人工重试；四类确定性模拟场景；已验网络实拍的全链路联调；MySQL 新链路验证；六页异常状态与设计回签；复现步骤、日志、截图和验收表。

### 不作为本周门槛的工作

真实短信账号、签名/模板审核与真实发送；真实充电运营商及 OCPP 联网；实时视频流；校园四类实拍与真实充电会话证据；新增准确率门槛；深色模式实施；登录鉴权；CSV 导出、统计下钻与桩详情弹窗。后三项设计差异应明确延期或改线框，不能默认为新增功能承诺。

响应 ≤5s、连续运行 ≥24h、前端分包与部署、正式技术报告/用户手册/结题报告继续由第四周完成。本周只采样耗时、发现运行阻断并准备材料，不提前声称性能达标。

### D1 口径建议（由 L1/T1/W1 共同落实，尚非现行契约）

1. **提醒来源**：正式请求提交的是记录 ID 与重试意图；“已提醒/失败”由发送器结果产生。旧 `notify_status` 入参的保留兼容或移除、响应状态与失败原因字段，写入契约再同步前后端。
2. **自动入口**：识别编排任务负责“取帧→识别→判定→落库→沙箱发送”；模拟器生成的违规走同一提醒服务。刷新图片、查询记录与查询统计均无发送副作用。
3. **占用身份**：建议新增稳定的占用标识，键采用“桩＋本次占用＋规则”，不要只用桩号或会在充电开始时被重置的 `start_time`。到车/换车创建标识、离车关闭；同次占用规则不变时复用记录，包括已提醒和失败；新占用可新建。所需字段、索引、历史记录兼容及迁移脚本先签定。
4. **提醒恢复**：本周以单个发送工作进程为运行基线；同一记录发送成功后不再自动发送，重复人工请求返回已有结果；失败由人工重试，最多 3 次发送尝试，达到上限给出明确结果。部署配置保存尝试上限，两个业务阈值仍只由 `system_config` 提供。尝试次数与结果必须持久化，不能重启后清零；并发请求需通过数据库状态约束避免重复执行。
5. **历史语义**：建议改阈值只影响后续判定，不回溯重算历史、不重新发送已成功提醒；对尚在占用的车辆，下次判定使用新阈值。三人确认后关闭 R10/T1 并补测试。
6. **失败语义**：无手机号或车主被删除时记录失败原因并允许补充绑定后重试；正常场景不创建违规提醒。无牌、依赖/权重缺失和坏帧不得伪造识别结果或静默切换 stub。
7. **证据边界**：实拍照片证明检测/号码/车型；充电状态和时间由模拟夹具提供，结果明确标注“网络实拍识别＋模拟充电状态＋沙箱提醒”，不称为真实短信或现场充电状态。

D1 下班前交付契约变更表、状态转移表、测试矩阵与三人确认记录。若关键口径尚未一致，继续做失败夹具和界面复核，不先实现互不兼容的接口。
